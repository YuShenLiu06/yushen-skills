# 交付前验收真实产物

## 执行

1. 固定待交付版本：记录最终源码 SHA、构建来源、平台／架构、产物名、版本和 SHA-256。代码或打包内容改变后，旧结果不能自动覆盖新产物；重建并重跑受影响的验收。
2. 走普通用户的真实入口：从实际下载链接取包，校验版本与哈希，解压或安装、双击启动，完成首次使用及本次交付的核心流程。仅启动开发服务器、打印 plan 或跑仓库源码不足以验收安装包。
3. 按实际流程检查风险点：权限字段和请求范围是否正确；真实授权后是否退出加载并进入可用状态；错误、慢网／断网、超时、取消、重复点击、返回、关闭重开及断点恢复是否可靠。记录操作、预期与实得结果；需要证实界面问题时留真实截图，不用示意图冒充。截图放 PR 评论／附件，不提交代码分支。
4. 分开报告测试层级，每层写范围、结果和证据。结果用“通过／失败／未测／阻塞／不适用”，不适用须说明理由。

| 层级 | 能支持的结论 |
| --- | --- |
| 单元测试 | 已测局部逻辑符合断言 |
| mock／离线 E2E | 模拟条件下的流程符合预期 |
| 实际 GUI | 对应平台和实际产物的界面操作结果 |
| 真实账户 E2E | 已获授权的真实账户与在线服务完整闭环 |

Windows／Mac 采用共核与独立入口时，分别打包、测试并给平台结论；一端通过不能覆盖另一端。GitHub Actions 构建 Release 时核验工作流的最终 SHA、产物和公开下载文件一致，实际下载并校验版本、哈希；CI 绿灯本身不证明用户路径可用。

给出交付结论和缺口。关键流程失败或尚未验证、平台未测、其他技术约束未过时，明确标“预览”，写清受影响的操作和补验条件；不能称正式可用。继续完成不依赖缺口的开发者测试，不把用户最终验收当替代。

## 验收

- 测试证据能追溯到最终 SHA 和具体产物；通过、失败、未测分别列出，数量不能代替覆盖范围或全通过结论。
- 核心路径从下载到真正可用，异步步骤有终态和可操作的恢复方式。
- 实际 GUI、真实授权或某平台受环境／权限限制时如实记未测或阻塞，不为补齐报告擅自更改账号权限。
- 交付说明先给可用范围和必要限制，日志、截图和检查明细放到可追溯的后附证据。

## 反例

- 500 个离线测试通过、真实账户授权未测：结论应为“离线流程通过；真实授权未验证，当前为预览”，不能写“全面通过”。
- Mac 包已实测、Windows 只编译成功：分别报告，Windows 保持预览；不要合并成“双平台已验证”。
